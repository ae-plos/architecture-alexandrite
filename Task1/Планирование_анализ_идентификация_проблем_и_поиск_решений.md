# Проблемы

## Категория проблем - схема

1. MES API предоставляется напрямую
2. На схеме отсутсвуют МСЭ и другие средства защиты
3. Хотелось бы добавить API GateWay и не два разнесенных фронта
4. Хранение статуса конкретного заказа размазано на 2 БД
5. Нет кэшей (об этом в задании 5)
6. MES db это Postgres и возможно одна из проблем это сохранение из MES многополигональных JSON 
7. Слишком разношерстный функционал у MES - нужно вынести расчеты в отдельную мастабируемую функциональность

## Категория проблема - процессы

0. Об вопросе производительности нужно было подумать до масштабирования бизнеса
1. Есть тестовое окружение - это дев, релиз или... прод. Формально для тестирование нужно развернуть количество стендов равное количеству тестировщиков
2. Так же нужно взять обратную связь, возможно разработчкам не хватает стендов из-за этого количесвто дефектов увеличилось (в принцепе узнать причину)
3. Нужно сделать нормальные пайплайны (для полной автоматизации)
4. React frontend разработчиков (1/2), возможно, будет недостаточно
5. По хорошему покрыть автотестами, в первую очередь пользовательскую историю

# Архитектура через полгода. В порядке приоритета

1. Нужно научить сервисы в горизонтальное масштабирование (причем выкупить ресурсы под горячий скейлинг с овербукингом до метрик, что бы не потерять 
   клиентов)
2. Сделать развертывание в проде с любым стеком логирования, который может быть быстро внедрен текущим специалистом (если стека нет)
   Для всех публичных методов классов добавить логирование идентификатора сущности, потока исполнения и метод (для горячего и самого дешевого поиска 
   текущих проблем). Так же очевидно ошибки там уже надеюсь есть.
3. Те критические проблемы, что были быстро выяслены, решить для того, что бы не было оттока клиентов
4. Введение метрик на сервисы, для отслеживания узких мест производительности, потому что нужно будет снизить овербукинг в облаке и в целом понимать, 
   где что работает возможно не эффективно
5. Далее, более введение трейсинга для запросов и состояний заказа, потому что скорее всего уже нет ошибок связанных с производительностью, но есть 
   ошибки реализации
6. Разбить MES сервис на два - работа с заказами в MES и расчетный сервис
7. Внедрение оркестратора для выполнения бизнес процессов BPMN (например Camunda) для доменов Заказ интернет магазина, Заказ MES
   Возможно, продумать сквозную логику и работу с двумя видами заказов как одним доменом
9. Сделать правильную маршрутизацию и МСЭ для внешних вызовов приложения (API GateWay)
10. Проработать моменты связанные с ретрай политиками и реализовать утвержденную схему
11. Проработать КЭШ write behind для заказов, что бы информация о новых была максильно быстро получаема на скроллерах

Как можно заметить, первые три пункта нацелены на сохранение конверсии клиентов и в реализации стоят минимальное количество ТРЗ. Плюс можно заметить,
что равномерная нагрузка на команду, девопс, тестирование и разработка (кроме фронта), а значит задачи могут быть выполнены в параллель.
