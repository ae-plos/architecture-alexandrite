# Анализ системы

В текущей задаче, у нас в любом свервисе может произойти сбой, и процесс выполнения заказа может быть прерва. Поэтому нам нужно внедрять трейсинг во 
все бек сервисы:
- Shop API
- CRM API
- MES API

## Данные, которые должны попадать в трейсинг:
- trace_id
- user_id - идентификатор пользователя, что бы быстро искать по 3ЛП
- order_id - идентификатор заказа как главный связыватель трейсинга для поиска в логах в ELK
- url_path - url сходящего запроса

# Мотивация

- Меньшее время на поиск проблем по жалобам пользователей
- Быстрее сам дефект будет устранен
- Качестно устранение дефекта будет выше, тк разработчик будет представлять более полную картину взаимодействий
- Структурирование для аналитики реального исполнения задач в распределеной системе (in-docs - as-is)

# Предлагаемое решение

Решение с файле jewerly_c4_tracing.drawio
Комментарий: в данной ситуации для первоначального внедрения, достаточно в памяти и all in one, если в дальнейшем система в количестве узлов будет 
расти - нужно поднять клик, и разделить сервис

# Компромиссы

В данной ситуации C# и тем более Java смогут метрики отдавать без особых "танцев в бубнами", но в нашей системе не так много межсервисных 
взаимодействий в первую очередь для которых внедряется данная функциональность. 
Так же с S3 все равно есть определенные проблемы с потерей файлов, а в MQ потери сообщений - и тут внедрение трейсинга бы помогло, но трудозатратно

# Безопасность

Как можно заметить на схеме есть блок инфраструктура - и я обычно предполагаю, что это условно отдельный контур, где аутентификация только на основе 
SSH ключей с ограничением по MAC-адресам и установленой фильтрацией MCЭ. Авторизация только под ролями команды разработки
