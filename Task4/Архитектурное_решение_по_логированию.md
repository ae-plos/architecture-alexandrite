# Сбор логов

INFO логи атрибуты всегда одинаковы, достаются через рантайм, что бы разработчик об этом не думал, а именно
1. trace_id
2. span_id
3. request_id
4. thread_id
5. parent_thread_id
6. user_id
7. method_name
8. method_params (all param.toString())

Сами методы:
1. Авторизация
2. Выполнение смены статуса, после успеха
3. Создание заказа

Да, конечно как минимум ERROR с тем же самым набором полей + текст ошибки от разраба и стектрейс
WARN для неуспешных авторизаций, ошибок запуска приложения не критических и не критических ошибок валидации
DEBUG будет в тестовых средах (см Task1)

# Мотивация

- Меньшее время на поиск проблем по жалобам пользователей
- Быстрее сам дефект будет устранен
- Точное понимание разработчиков, что было в качестве параметров в текущем исполнении

Работу с пользователями нужно первым повесить на логи и трейсинг, тк потери клиентов это серьезная проблема бизнеса, остальное по мере возможности

# Предлагаемое решение

Решение с файле jewerly_c4_logs.drawio
Чувствительные данные в лог не попадают, тк для них будет использоваться спициальные объекты строк, у которых переопределен метод toString() 
    (либо можно библиотеку с аннотациями настроить)
Доступ к логам, ровно так же как и к трейсам

Политика - в данном проекте нет серьезных требований и устанавливать их не имеет смысла. А значит нам достаточно будет обычной рециркуляции 2 месяца и 
    очистка. Индексы - разбиты по сервисам + 2 недельная давность

# Система анализатор логов

## Аллертинг:
1. Ошибки сервиса чаще чем раз в час
2. Ошибки + избранные method_name

## Анномалии
1. thread_id + request_id не изменяется более 1 часа
2. Нет логов сервиса более 1 часа
